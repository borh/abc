# ADR 0021: Person Identity Drift Harness Contract

Status: Accepted
Date: 2026-04-29
Accepted: 2026-04-30

## Context

ADR 0020 chooses a lineage-only drift model: drift events are audit sidecars,
not manifest-identity inputs. It also chooses ABC-local IDs and stable event IDs
with participant indexes. This ADR defines how those events are represented on
disk, converted to RDF, validated, and surfaced by `validate-design-bundle`.

Two existing implementation facts shape the harness:

- `validate-persons-directory!` in `abc.tools.validate-design-bundle` scans
  immediate `*.json` files under `examples/v0/example-persons` as person
  records. Drift sidecars therefore cannot be flat files such as
  `<person_id>.events.json` in that directory.
- `abc.tools.shacl/validate!` calls Jena's plain `ShaclValidator/get` with no
  RDFS inference. Subclass axioms in `schemas/manifest.shacl.ttl` document the
  vocabulary but do not make `ActivityShape` target bare `abc:DriftEvent` nodes.

## Decision

### File layout

Per-event files live at:

```text
examples/v0/example-persons/_events/<drift_event_id>.json
```

Per-person index sidecars live at:

```text
examples/v0/example-persons/_indexes/<person_id>.json
```

Both are subdirectories, so the current immediate-level person-record discovery
filter skips them.

### File format

Each drift event is wrapper JSON:

```json
{
  "schema_id": "https://w3id.org/abc/schemas/person-drift-event.schema.json",
  "schema_hash": "sha256:...",
  "drift_event_id": "sha256:...",
  "drift_event_type": "split",
  "date": "2026-...",
  "participants": [
    {
      "snapshot_id": "pre-000123",
      "person_id": "000123",
      "person_record_hash": "sha256:..."
    },
    {
      "snapshot_id": "post-abc-deadbeefcafe",
      "person_id": "abc-deadbeefcafe",
      "person_record_hash": "sha256:..."
    }
  ],
  "evidence": ["https://..."],
  "prov": {
    "used": ["pre-000123"],
    "was_generated_by": ["post-abc-deadbeefcafe"],
    "qualified_association": {
      "agent": "https://w3id.org/abc/agents/...",
      "had_role": "abc:DriftEditor"
    }
  }
}
```

The JSON field names use `snake_case`; RDF predicates use `prefix:local`.

- JSON `drift_event_id` has no RDF predicate.
- JSON `drift_event_type` maps to RDF `abc:driftEventType`.
- JSON `date` maps to RDF `dcterms:date`.
- JSON `participants[]` is the canonical participant snapshot list and has no
  direct RDF predicate. Each item is an object with `snapshot_id`, `person_id`,
  and `person_record_hash`.
- JSON `evidence[]` maps to RDF `abc:driftEvidence`.
- JSON `prov` carries only `used`, `was_generated_by`, and
  `qualified_association`. These keys map to RDF `prov:used`,
  `prov:wasGeneratedBy`, and `prov:qualifiedAssociation`.

Canonical ordering is part of the file format:

- `participants[]` is sorted lexicographically by `snapshot_id`.
- `prov.used` and `prov.was_generated_by` are each sorted lexicographically.

JSONL is rejected for the recommended layout. There is one event per file, so
append-only ergonomics are not needed, and wrapper JSON preserves top-level
`schema_id` plus `schema_hash`.

### JSON `prov` block as minimal contract

The canonical RDF graph includes six PROV predicates, but JSON explicitly
carries only three. The committed JSON shape is a predicate-keyed object, not
JSON-LD:

```json
{
  "used": ["pre-000123"],
  "was_generated_by": ["post-abc-deadbeefcafe"],
  "qualified_association": {
    "agent": "https://w3id.org/abc/agents/...",
    "had_role": "abc:DriftEditor"
  }
}
```

The snapshot IDs in `used` and `was_generated_by` are local references to
`participants[].snapshot_id`. `event->graph` resolves them to snapshot IRIs
using the participant's `person_id` and `person_record_hash`.

`had_role` is a CURIE string. In v0 its closed enum is `abc:DriftEditor`;
widening the role set requires a later ADR. `event->graph` resolves the CURIE
through the project prefix map; `abc:DriftEditor` resolves to
`https://w3id.org/abc/DriftEditor`. Unknown prefixes or any other role value
are validation failures. `agent` is a full IRI string and must be syntactically
valid.

`event->graph` derives the remaining RDF predicates:

- `prov:wasInvalidatedBy`: for every pre-snapshot Entity used by the Activity,
  emit `pre-snapshot prov:wasInvalidatedBy activity`.
- `prov:wasAssociatedWith`: derive the unqualified association from the
  `prov:agent` inside the qualified Association.
- `prov:wasDerivedFrom`: for every post-snapshot generated by the Activity and
  every pre-snapshot used by the Activity, emit `post prov:wasDerivedFrom pre`.

This keeps the editor-facing JSON contract smaller and avoids hand-maintained
duplication between qualified and unqualified PROV edges.

### RDF type materialization

`event->graph` materializes every required `rdf:type` directly in the data
graph:

- Every event node gets `rdf:type abc:DriftEvent`.
- Every event node gets `rdf:type prov:Activity`.
- A split gets `rdf:type abc:DriftSplitEvent`.
- A merge gets `rdf:type abc:DriftMergeEvent`.

Subclass axioms are still added to `schemas/manifest.shacl.ttl` for vocabulary
documentation:

- `abc:DriftEvent rdfs:subClassOf prov:Activity`
- `abc:DriftSplitEvent rdfs:subClassOf abc:DriftEvent`
- `abc:DriftMergeEvent rdfs:subClassOf abc:DriftEvent`

Current validation does not depend on those axioms.

### Typing pre-check and SHACL shapes

`validate-drift-events!` runs a typing-coherence pre-check before SHACL:

- Derive the expected type set from JSON `drift_event_type`.
- Collect the actual `rdf:type` set from the materialized RDF graph.
- Fail on missing, unexpected, or wrong types with a distinct failure entry.

`schemas/manifest.shacl.ttl` adds three SHACL shapes:

- `PersonDriftEventShape`, targeting `abc:DriftEvent`, checks
  `abc:driftEventType`, `dcterms:date`, `abc:driftEvidence`, and
  `rdf:type prov:Activity`.
- `PersonDriftSplitEventShape`, targeting `abc:DriftSplitEvent`, requires
  exactly one `prov:used`, at least two inverse `prov:wasGeneratedBy` edges, and
  RDF `abc:driftEventType "split"`.
- `PersonDriftMergeEventShape`, targeting `abc:DriftMergeEvent`, requires at
  least two `prov:used`, exactly one inverse `prov:wasGeneratedBy` edge, and RDF
  `abc:driftEventType "merge"`.

The base shape's `rdf:type prov:Activity` requirement is a SHACL backstop for
hand-crafted TTL fixtures. `ActivityShape` itself fires only when the data graph
contains `rdf:type prov:Activity`.

### Snapshot-to-person mapping

PROV edges point to snapshot Entities, not directly to person IDs. Snapshot
Entities use:

```text
https://w3id.org/abc/persons/<person_id>#snapshot-<person_record_hash_short>
```

`event->graph` derives `<person_record_hash_short>` from the
`person_record_hash` stored in the event's `participants[]` item. The short
hash is the first 12 lowercase hex characters of the digest after the `sha256:`
prefix. `event->graph` must not read the current person record to discover the
hash, because that would rebind historical events after later bibliographic
edits.

The `#snapshot-` fragment is a deliberate hash-IRI design, not a separate
HTTP resource. A snapshot is a PROV-O specialization of a person and lives in
the same document namespace as the person IRI; dereferencing the snapshot IRI
returns the person document (the fragment is resolved client-side within that
document). This follows the common LOD pattern where a `specializationOf`
target shares the document of the general thing. The implication for HTTP
consumers is recorded: a snapshot IRI is **not** independently dereferenceable,
and clients that fetch the snapshot IRI receive the person resource rather
than a per-snapshot representation. A future ADR may mint slash-IRI snapshot
paths if independent per-snapshot content negotiation is required; that would
rotate committed drift fixtures and is therefore deferred.

Each snapshot Entity carries:

```text
<snapshot> prov:specializationOf <person-iri>
```

The JSON `participants[]` array is the canonical participant snapshot list for
index integrity. `validate-drift-events!` cross-checks it against the person IDs
and snapshot hashes derived from snapshot IRIs and `prov:specializationOf`
targets.

`validate-drift-events!` also enforces JSON graph coherence that JSON Schema
cannot express:

- Every `prov.used` and `prov.was_generated_by` value resolves to exactly one
  `participants[].snapshot_id`.
- Every participant `snapshot_id` appears in exactly one of `prov.used` or
  `prov.was_generated_by`.
- No participant appears in both arrays.
- Every `snapshot_id` is unique within `participants[]`.
- `snapshot_id` prefixes match usage: `pre-` for `prov.used`, `post-` for
  `prov.was_generated_by`.
- The canonical ordering rules are followed.

The event JSON Schema enforces only local shape constraints and type-dependent
array cardinalities: for a split, exactly one `prov.used` and at least two
`prov.was_generated_by`; for a merge, at least two `prov.used` and exactly one
`prov.was_generated_by`. Resolution and coverage are validator checks.

### Index artifact contract

Per-person index sidecars have their own JSON Schema:

```text
schemas/person-drift-index.schema.json
```

The wrapper shape is:

```json
{
  "schema_id": "https://w3id.org/abc/schemas/person-drift-index.schema.json",
  "schema_hash": "sha256:...",
  "person_id": "000123",
  "drift_event_ids": ["sha256:..."]
}
```

No `PersonDriftIndexShape` is materialized. The index is a JSON traversal
artifact, not a semantic RDF node.

`validate-drift-events!` enforces three referential-integrity rules:

- Every `drift_event_ids[i]` resolves to an event file under `_events/`.
- Every event appears in every participant person_id's
  `_indexes/<person_id>.json`.
- No orphan event file exists under `_events/` without any index reference.

### Harness integration

`validate-design-bundle` invokes `validate-drift-events!` unconditionally.

Return shapes:

- `{:status :not-present}` when no drift artifact is present.
- `{:status :ok :events N :indexes M}` when all drift artifacts validate.
- `{:status :error :failures [...]}` when validation fails.

Validation order:

1. Validate each event JSON against `person-drift-event.schema.json`.
2. Run JSON graph-coherence checks: snapshot resolution, participant coverage,
   disjoint predecessor/successor membership, `snapshot_id` uniqueness,
   prefix/usage consistency, canonical ordering, `had_role` enum/CURIE
   resolution, and `agent` IRI syntax.
3. Convert event JSON to RDF with `event->graph`.
4. Run RDF typing-coherence and participant/PROV cross-checks.
5. Run SHACL against the event graph.
6. Validate each index against `person-drift-index.schema.json`.
7. Enforce referential-integrity rules.

Negative drift fixtures live under:

```text
fixtures/v0/invalid/drift/
```

They use a new `validate-drift-fixtures!` runner, sibling to
`validate-tei-schematron!`, because the TEI runner is XML/Schematron-specific.

## Hard Rule

For the ADR 0020 recommended path:

- `manifest.json` is byte-identical before and after adding a drift event.
- `examples/v0/example-persons/<person_id>.json` files are untouched.
- `person_record_hash` and `metadata_record_hash` are unchanged by drift
  artifacts.
- The drift-event and drift-index schemas do not flow into
  `manifest_identity_object`.
- If ABC-local IDs are implemented in the same milestone, their schema-widening
  cascade is verified separately from the drift-artifact invariant.

This invariant is scoped to drift artifacts themselves. A real split may also
introduce new person records or edit metadata contributors; those ordinary
record changes follow the existing Flavor 1 hash cascade and are not covered by
the drift-artifact byte-identity rule.

## Acceptance Criteria

- `schemas/person-drift-event.schema.json` exists and validates the wrapper JSON
  event shape.
- The event schema requires each `participants[]` item to carry `snapshot_id`,
  `person_id`, and `person_record_hash`, and enforces split/merge cardinalities
  for `prov.used` and `prov.was_generated_by`.
- `validate-drift-events!` proves `prov.used` / `prov.was_generated_by` values
  resolve to participant `snapshot_id`s, every participant is covered exactly
  once, no participant appears as both predecessor and successor, and canonical
  ordering is enforced.
- `validate-drift-events!` rejects any `had_role` other than
  `abc:DriftEditor`, any unresolved CURIE prefix, and any syntactically invalid
  `qualified_association.agent` IRI.
- `schemas/person-drift-index.schema.json` exists and validates index sidecars.
- `schemas/manifest.shacl.ttl` includes `PersonDriftEventShape`,
  `PersonDriftSplitEventShape`, `PersonDriftMergeEventShape`, and the three
  subclass axioms for vocabulary documentation.
- Unit tests prove `event->graph` materializes `rdf:type` triples and derives
  `prov:wasInvalidatedBy`, `prov:wasAssociatedWith`, and
  `prov:wasDerivedFrom`.
- Unit tests prove `event->graph` derives snapshot IRIs from event-embedded
  `person_record_hash` values, not from current person records on disk.
- Unit tests prove `validate-drift-events!` catches typing-coherence,
  JSON graph-coherence, participant-mismatch, and referential-integrity
  failures.
- The example bundle contains one fictional split event under `_events/` and
  participant indexes under `_indexes/`.
- Negative fixtures cover base shape failures, derived-predicate failures,
  split/merge cardinality failures, typing-discipline failures, participant
  mismatch, and the three referential-integrity rules.
- `nix flake check` passes.
- Adding the drift artifacts does not rotate `manifest.json` or
  `manifest_identity_object`.

## Consequences

- The harness gains one new validation surface and one new negative-fixture
  runner.
- The drift event JSON stays smaller than the RDF graph; consistency of derived
  PROV edges is enforced by the emitter and unit tests.
- SHACL validation remains under the current no-inference wrapper. Future
  inference-aware validation can use the subclass axioms, but current
  correctness does not depend on them.
- Consumers can discover drift events locally through per-person indexes without
  scanning every event file.
